产品演进说明

从第一版到现在：
织忆做了什么，为什么改

织忆（Memloom）的起点是一个通用的个人知识沉淀工具：把用户与 AI 的对话自动变成可复习的知识。第一版做出来并对外分享后，用户访谈告诉我们"通用知识库"缺少真正的落地场景，于是我们把它收窄为面向研究生的科研知识协同层，机制也从"帮人记住"改成"人与 Agent 双向连接"。下面先讲这条路怎么走过来，再从「01 项目背景」开始完整介绍现在这一版。

01 项目背景

1.1 AI 已经走进真实科研工作流

过去两年里，研究者使用 AI 的方式发生了本质变化。AI 不再只是一个查资料的搜索框，而是深度参与到真实的科研过程中：研究者用它讨论方案、推导思路、写和改代码、修订论文、分析实验结果、准备组会与 rebuttal。科研知识的一部分，正在从静态的文档与笔记，转移到人与 AI 持续往返的协作过程里。

这意味着，研究者每天都在和 AI 产生大量高密度对话。这些对话里真正有长期价值的，是其中沉淀出的认知增量：方法论、判断标准、领域陷阱、长期偏好这类未来还会反复用到的东西。

1.2 一个被忽视的新问题：高频协作没有形成复利

核心问题只有一个：没有沉淀。今天的工具几乎都只盯着"过程"——把对话、任务、代码一条条记录下来，却不管这个过程里真正产出的认知有没有被吸收。结果是人在一次次协作里明明学到了东西，却没把它变成自己的判断和方法论，能力并没有真的增长；下次遇到相似的问题，还是得从头问、从头想。

Agent 这一侧同样缺位。它现在能依赖的多半是通用记忆系统，记的是"用户叫什么、偏好什么风格、上次聊过什么"这类零散事实，而不是科研真正需要的东西——已经被确认的判断、踩过的坑、方法论、研究脉络的演化。于是人没沉淀、Agent 也没沉淀，下次它处理相关任务时依然做不好。这才是高频协作没有形成复利的根源：每一次本该让人和 Agent 一起变强的协作，最后都像从零开始。

1.3 织忆是什么：科研场景的人—Agent 双向连接

织忆是面向 AI-native 科研的知识协同层。它从研究者与 Agent 的协作记录中提取长期有价值的科研知识，经过用户轻量审核后，沉淀成一套既能帮助人复盘理解、也能帮助 Agent 继续调用的知识资产。

这里的"双向连接"指同一条科研知识有两种使用形态：对人，它要能被理解、复盘和迁移；对 Agent，它要能被调用、约束和更新。两端共享同一条经过审核的知识，内容不会各自维护、彼此漂移。科研场景进一步决定了这些知识还必须处理来源、证据、边界、版本、冲突与审核。

"织忆让人与 Agent 在同一套持续生长的科研知识上协作。"

1.4 为什么是现在

这件事以前做不了，是因为 AI 还没有稳定参与复杂的科研讨论，也没有形成足够多的人机协作记录。如今，聊天、代码、写作、实验日志和项目文档都在持续数字化，系统可以从这些痕迹里识别出长期知识；Agent 也越来越深地参与科研，越来越需要和人共享同一套已确认的知识。

这里有一个我们最核心的判断：模型能力越强，人和 Agent 之间的知识错位反而越隐蔽、代价也越大。当 AI 看起来什么都能答时，人很容易误以为自己已经掌握，Agent 也很容易在缺少用户真实判断时给出"看似合理却偏离脉络"的答案——能力越强，这种错位越不容易被当场发现，等到实验、论文或评审里暴露出来时，代价已经产生。技术条件（深度协作、数字化痕迹、结构化输出能力）与需求强度（错位代价上升）在此刻同时成立，正是现在该做这件事的原因。

图 1 · 核心创新框架　科研场景下人与 Agent 的双向连接：同时研究人端需求与 Agent 端需求，并修复二者独立工作时产生的断裂。

02 解决的痛点

核心问题是高频科研协作没有形成复利。这种失效有三个层次，并在科研场景中被显著放大。

2.1 三种"增长失败"

理想中协作带来的三重增长，现实中每一种都可能失败：

失败层次表现
人端能力没有沉淀AI 帮助完成了任务，但任务完成不等于能力增长。用户和 AI 讨论了很多概念、方法和方案，却没有真正形成自己的理解、判断和方法论，后续也就难以判断、约束和驾驭 Agent。
Agent 端知识没有延续Agent 参与过很多讨论，但跨 session 之后仍然容易退回通用水平。如今虽已有通用 Memory，但它记的是偏好、昵称、零散事实，并不适配科研这个设定——它不知道哪些内容已被确认、哪些只是临时猜想、哪些旧结论已被推翻，因此很难持续输出贴合研究脉络的答案。
双方知识状态不同步即使人和 Agent 各自有些长进，也可能不是同一套长进：人已经更新了判断，Agent 还在沿用旧结论；Agent 记住了局部偏好，人沉淀的却是更深的方法论。这是其中最隐蔽的一层。

这些问题最终都表现为后续协作质量下降：用户反复解释背景，Agent 输出不贴合脉络，写作、组会和研究计划里出现判断漂移、版本混乱、表达不符合既有方法论。更根本的是，人因为能力没有真正进化，下次很可能依然做不好这件事、提不出更好的思路，也给不出能让 Agent 做对的指挥。

图 2 · 协作复利失效　每一次协作本应带来人、Agent 与共享知识的复利，但三条增长曲线都可能在沉淀环节断裂。

2.2 科研场景为什么把代价放大

在普通对话里，一条知识没沉淀、或人和 Agent 各记一个版本，代价往往很小——重新问一遍就好。但科研知识不是普通文本：它带着来源、证据、适用边界、版本和过期风险。一条结论可能只在某类实验条件下成立、可能已被后续工作推翻、也可能只是 AI 一种"听起来合理"的猜测。当这样的知识被悄悄沿用、或人机各执一个版本时，上一节那三种失败就不再是"重新解释一下"的小事，而会被放大成走错方向的实验、站不住的论文段落、过不了的评审。

正因为科研知识对来源、版本、边界、过期如此敏感，它不能靠通用记忆草草存下，而必须被专门设计：来源要标注、版本要管理、边界要约束、过期要标记。这套结构对普通用户是负担，对研究者却是刚需——也正是现有工具普遍缺失的部分（见 2.3）。

2.3 现有方案的结构性盲区

用户当前通常用 Notion、Obsidian 等笔记软件维护知识，或者用 CLAUDE.md、AGENTS.md 让 Agent 维护知识，但这些方案都只能解决一部分问题：

现有方案能做什么结构性盲区
文档 / 笔记工具
Notion · Obsidian · Zotero		擅长保存内容不保证人真正内化，也不保证 Agent 会用
Agent 规则文件
CLAUDE.md · AGENTS.md · Cursor rules		适合让 Agent 执行人的理解弱、知识演化弱，容易积累"Agent 能执行但人说不清"的黑箱
通用 memory
平台内置记忆		适合轻量上下文与偏好不会为科研知识承担重的分类、审核和版本结构；学习结果不回流为 Agent 约束
人工整理灵活、可控成本高、不可持续

所以当下用户在用一组不完整的方法硬解决。织忆要补的，是这些工具之间缺失的"科研知识生命周期层"。

2.4 来自真实用户访谈的信号

2026 年 6 月对研究生群体的访谈，验证并修正了我们对痛点的理解。

"我觉得这个需求是对的，或者说是有必要的……我在下一次操作时，可能忘记了流程中的某一个关键点，这是很有可能的。"

底层需求（高频 AI 对话中存在被忽略但有价值的知识）被确认存在。同时，访谈暴露了几个对产品设计影响重大的真实关切（如何落进设计，主要见第六部分未来规划）：

真实信号含义
知识需要分级用户高度关心"系统能否分清重要 vs 不重要、需要深入应用 vs 只需了解"，不希望被堆成一摞同质卡片。
复习动机是最大风险"即便东西被很好地整理了，用户有多大动力去复习？"——任何形式的主动复习都缺乏自然驱动力，这是闭环里最脆弱的一环。
定位应是"陪伴"而非"导师"用户质疑 AI 当导师的能力边界，主动提议把定位放在"陪伴、提醒、一起回顾"，而非"像导师一样深度引导"。
调研整合是高频刚需用户主动描述："把 N 次 AI 对话整合成一份给导师 / 同事看的报告"——动机极强、发生频繁。

03 产品方案与核心闭环

织忆只做一个核心动作：把 AI 协作记录和历史知识，转化为经过用户审核的科研知识对象。围绕这个动作，构建一条由人把关的知识闭环。

3.1 产品形态：本地优先的双端知识软件

织忆是一个本地优先的科研知识软件，和 Codex、Claude Code 这类 Agent 工作台配合使用。它由两部分组成，共享同一套知识对象：

端形态职责
人端可视化桌面界面知识管理、审核、复习、内化、关系理解——让用户把知识变成自己的能力。
Agent 端知识服务（记忆注入 / MCP）向用户正在使用的 Agent 提供重组后的知识包、上下文包与任务约束。最终的报告、代码、论文段落仍由用户自己的 Agent 生成，织忆只提供已确认的判断与上下文。

两端使用后的反馈再反过来修正这条知识：人端暴露误解，Agent 端暴露误用，系统据此更新知识对象。这构成了"双向连接"的闭环本质。

3.2 什么是"知识对象"

织忆的最小资产是经人审核的知识对象（Knowledge Object）。一个知识对象包含类型、来源、核心判断、适用范围、证据、反例、版本状态，以及面向人与面向 Agent 的两种使用形态。其中两点最关键：

双形态（Dual-Source）

同一条知识同时维护 Agent 版本（给 AI runtime 调用的自包含规则、约束、调用条件）与 Human 版本（给人理解和复盘的解释、机制、边界、例子）。记忆注入给 Agent 时只抽取 Agent 版本，避免把面向人的复盘解释塞进 Agent 上下文。两个版本必须同步演化，不允许彼此漂移。

形态三分法（Form）

每条知识被归为三种形态之一，它决定了这条知识主要给谁用、以及怎么加载：

形态主要读者含义与例子
practice
实践规则		Agent可执行的操作规则、SOP、反模式、个人风格、边界。如"做 X / 不做 Y / X 在 Y 时不适用"。
methodology
方法论		人 + Agent带"为什么"的判据、评估框架、启发式。如"判断 X 看 Y / 通常 X 时优先 Y"。
theory
理论理解		人机制解释、一阶原理、边界成因。如"X 的本质是 Y / X 因 Z 而成立"。

此外，每条知识带有严格的来源归责（Attribution）：明确区分这条判断来自用户立场、AI 解释、外部资料还是工具观察，并标注采纳程度。系统绝不把 AI 的解释或外部资料伪装成"用户已采纳的判断"——这是科研知识可信度的底线。

3.3 五阶段核心闭环

知识在织忆中流经五个阶段，构成产品统一的核心逻辑（最后的"使用"阶段分别面向 Agent 与人）：

阶段做什么用户感知结果
Distill 提炼读取本地 Agent 会话，增量抽取长期有价值的候选知识系统从协作记录里发现了少量高价值候选
Merge 融合判类把候选与已有知识比对，判定为新增 / 关联 / 更新 / 重复，并补充关系链系统判断这条候选是新的，还是该更新 / 关联旧知识
Review 审核用户逐条确认、修改、拒绝或应用更新用户用低成本判断"记住 / 忘掉 / 稍后 / 修改"
Canonical 正式入库通过审核的内容进入正式知识库形成可长期复用的知识资产
Retrieve 检索注入把已审知识检索、注入给 Agent 调用下次 Agent 协作更贴合研究脉络
Recall 复盘回顾按遗忘曲线把知识推给人主动回顾人能持续巩固理解、把知识变成能力
图 3 · 知识生命周期框架　围绕输入、知识生命周期管理、输出三个阶段，管理科研知识从协作中产生、被确认、被保存、被人与 Agent 重新使用的完整过程。

3.4 人在循环中：作为质量机制

织忆与全自动 memory 最根本的区别，是把人的审核作为质量机制。核心假设是"AI 负责发现候选，人负责判断价值"。全自动系统容易把日常噪声、一次性任务细节、通识内容和模型自己的总结都写入记忆，最终噪声压过信号。人的介入恰好解决三个矛盾：

矛盾全自动系统的问题织忆的解法
全面 vs 精简什么都收，噪声压过信号候选必须经过轻量审核
新知识 vs 旧知识容易重复、覆盖或错误融合AI 只建议关系，人来拍板
Agent 用 vs 人学习单一格式无法同时服务两类读者同一知识源派生两套视图

审核的目标是在保证知识库质量的同时，让用户在判断中重新理解这些知识。判断标准很硬："未来 Agent 如果不知道这条，会不会明显做差？"——通识定义默认不进库，个人理解可以进，可执行判断强烈应该进。

3.5 一个典型场景

异步共识协议讨论 · Demo 用户和 AI 多轮讨论异步共识协议，织忆提炼出一条方法论："某类异步共识通过前置信息、承诺或权重累积，弥补无全局同步时钟下的定序困难。"

· 对人：它变成一条可复习、可迁移的方法论，下次分析新协议时能主动想起；
· 对 Agent：它变成分析新协议时可调用的推理框架；
· 当出现反例或修正时：系统更新这条知识，旧结论与新结论不会混在一起。

最小可行产品把上面的五阶段端到端走通一条最小闭环：导入协作记录 → 抽取候选 → 审核与融合 → 人端内化 / Agent 调用 → 使用反馈修正知识。

04 技术架构

织忆是一个由确定性流水线驱动、以人审为质量门槛、本地优先的知识提炼与检索系统。架构的每一处设计，都服务于"高质量、可追溯、可迁移"这三个目标。

4.1 总体架构：一图看懂

织忆是一条由人把关、本地优先的知识流水线。上行方向，系统从本地 Agent 会话中提炼候选、自动判类、经人审核后写入权威知识库；下行方向，同一套已审知识分别输出给人（复盘）与 Agent（记忆注入与调用）；使用反馈再回流，持续修正知识，构成双向闭环。下图给出完整的数据流与分层结构。

图 4 · 织忆系统架构　五个层次自上而下：数据源 → 执行引擎 → 人工审核质量门槛 → 本地知识存储 → 双端输出；右侧为模型层，底部为贯穿全局的设计不变式，并以使用反馈回路构成双向闭环。

这张图呈现的是能力的最终形态。下面分两步说明它是怎么来的：先用一组 Skill 把这条闭环跑通、验证可行（4.2），再用客户端把同样的能力编排成可控、可观测的产品（4.3）；图中各层与下文小节一一对应。

4.2 第一步：用 Skill 验证核心闭环

织忆没有一上来就做大产品，而是先用最轻的形态验证核心逻辑：把五阶段闭环实现为一组可安装进本地 Agent（Claude Code / Codex）的命令行 Skill，先回答几个关键问题——抽取能否找到真正高价值的候选、用户是否愿意审核、确认后的知识能否改善后续协作。六个 Skill 各司其职，并按固定关系串成一条流水线：

Skill职责
init搭建并校验本地知识库布局，纯确定性、永不覆盖已有文件
distill从会话增量抽取长期有价值的候选知识
merge把候选与已有知识比对判类（新增 / 关联 / 更新 / 重复），并补充关系
review人审：接受 / 拒绝 / 编辑（后端不调 LLM、不改知识含义）
retrieve把已审知识检索、注入给 Agent 调用
recall按遗忘曲线给人做复盘

它们的衔接关系就是核心闭环本身：init 铺好底座，distill → merge → review 把会话变成已审知识写入 canonical，再由 retrieve（对 Agent）与 recall（对人）双向输出。六个 Skill 中有五个是纯 Python 3 标准库、零第三方依赖，只有 review 需要 Node——刻意保持极轻，既便于嵌入真实工作流、降低信任成本，也让"这条闭环是否成立"能被快速、低成本地验证。

4.3 第二步：客户端——把能力编排成产品

在 Skill 验证了可行性之后，我们才开始做面向最终用户的桌面客户端。关键在于：客户端把同一套五阶段能力重新实现为一条被明确编排的引擎流水线，没有把六个独立 Skill 拼起来顺序执行。

我们选择 OpenAI Agents SDK 作为轻量 agent 框架，刻意不用 LangGraph 这类重编排：流水线以"有界结构化调用"跑在框架上，按阶段顺序推进、可断点续跑，不让模型自主漫游；每一步的输入输出都经 Zod 校验，失败即停、绝不静默降级。这条管道覆盖闭环的上行段（从会话到进入待审），依次完成增量读取（按游标只取主会话新增内容）、结构化抽取、批内融合（合并被拆碎的同一知识）、四类判类（先召回邻居再精判 duplicate / update / link / none）、落盘与关系补链；其后的人工审核、检索与复盘由各自模块承接。换句话说，Skill 提供了"能力单元"，客户端提供了把这些单元编排成可控、可观测、可解释系统的工程。

客户端技术栈为 Electron 39 + React 19 + MUI + Vite + TypeScript，逻辑上分为职责清晰、互不越界的四层：

层级职责技术
UI 层知识管理、审核、复习、关系展示React 19 + TypeScript + Material UI
引擎层多阶段流水线：提炼 / 融合判类 / 关系补链 / 复盘TypeScript + OpenAI Agents SDK，确定性编排
存储层本地知识存储，无数据库本地 JSON，原子写
模型层结构化模型调用GPT-5.5，支持自主配置，密钥加密存储

可解释性：抓取衰减漏斗

编排引擎同时产出运行记录与漏斗遥测——读取轮次 → 初始候选 → 融合后 → 进入待审 → 重复 → 失败 → 留存率。这把"读了很多对话，为什么候选不多"从"缺陷"重新解释为质量机制：系统在主动过滤一次性任务与无长期价值的信息，只留下少量高价值候选。

示例文案 本次读取 148 轮对话，生成 23 条初始候选，融合后剩余 12 条，其中 5 条进入待审、7 条判为重复。留存率 3.4%，说明系统只保留长期有价值的知识。

4.4 为科研而设计的知识对象

织忆的最小资产是经人审核的知识对象，这是为科研知识的可信要求专门设计的结构化对象，由 Zod + TypeScript 强类型定义，运行时校验与编译期类型推导统一。三处设计体现了它的完备性：

双形态（Dual-Source）。同一条知识同时维护 Agent 版本（自包含规则、约束、调用条件）与 Human 版本（解释、机制、边界、例子）；注入给 Agent 时只抽取 Agent 版本，两个版本必须同步演化、不允许漂移。

形态三分（Form）。每条知识归为 practice（实践规则，主要给 Agent）、methodology（方法论，人与 Agent 共用）或 theory（理论理解，主要给人）之一——它决定这条知识主要给谁用、以及怎么加载。

严格归责（Attribution）。每条知识用 kind / claim_owner / adoption 三个字段严格配对，明确判断来自用户立场、AI 解释、外部资料还是工具观察，并标注采纳程度；系统绝不把 AI 解释或外部资料伪装成"用户已采纳的判断"——这是科研知识可信度的底线。

知识库以一组本地 JSON 文件组织，其中 canonical 为权威源，索引与分领域视图均为可随时重建的派生产物。

4.5 工程严谨性

除了上面的编排与数据模型，几处工程约定共同构成产品可信度的底层保证：

  • 分层隔离：主进程 / 渲染层 / 共享契约三个源码树严格分离，类型与 IPC 通道由共享层统一约束。
  • 密钥安全：渲染层不持密钥、不直接调模型，全部经 IPC 走主进程；密钥加密存储，永不写入明文配置文件。
  • 数据安全：所有知识写入都是整个 JSON 文件的原子替换，避免半写损坏。
  • 可测试性：引擎与存储测试使用 fake runner + fake model client 保证确定性，不依赖真实模型即可完整回归。
  • 低门槛：设置项中只有模型密钥必填，其余皆有合理默认值。

4.6 对外交付：双端输出

对应架构图最下方的"双端输出"层，交付坚持一条硬边界——只交付已审知识，不替用户生成最终产物（报告 / 代码 / 论文）。对人是复盘中心（主动回忆、费曼追问）；对 Agent 提供两条由轻到重的路径：复制文本（零配置粘贴）、记忆注入（默认主路径，生成 .memloom/ 与 AGENTS.md / CLAUDE.md 查阅指引，知识更新后自动重生成）。未来的 MCP 定制化输出（见 6.3）会在此之上提供更丰富的输出形态，但同样以"基于已审知识、可追溯、不虚构"为前提。

关于检索的一个务实选择 织忆的知识对象本身就是结构化的小文档。喂给 Agent 时，直接用目录索引 + 文件检索（与当前 Claude Code 的做法一致）比建向量库更轻量、更准确，也避免了 RAG 在精确查询场景下的偏差。这与一线研究生用户的判断相吻合。

4.7 设计不变式

前面几节的设计可以归纳为六条贯穿全局的不变式（也是架构图底部那条带），它们是对前文设计的统一约束：本地优先（数据默认存本机、可导出可删）、双源不漂移（Agent 版本与 Human 版本同步演化）、单源真理（canonical 权威，索引与视图皆可重建）、人在循环（最终入库决策权在人）、严格归责（来源绝不伪装）、结构化校验（LLM 输出经 Zod 校验、失败即停）。

05 商业化

个人与开源负责引流和沉淀用户，课题组（PI）是核心付费群体，学校与科研院所做规模化。这是一条"学生用得爽、课题组买单"的 student-pulled lab SaaS 路径。

5.1 目标用户：为什么先做研究生

第一批用户是高频使用 AI 的研究生，包括博士生、科研型硕士、博士后，以及青年 PI。选择研究生，是因为他们身上几个客观特征同时成立：AI 使用频率高、研究过程有大量数字化痕迹、知识需要反复复用；这些特征叠加，正好让人端需求与 Agent 端需求同时变强，也就是"双向连接"最该出现的地方：

人群特征适配度
研究生以下输入多，但真实产出与长期项目少人端学习强、Agent 端复用弱，更适合 Anki / NotebookLM
研究生输入与输出同时旺盛：持续读论文、学方法，同时做实验、写代码、写论文、备组会、rebuttal；知识体系一直在变人端需求与 Agent 端需求最容易同时出现
已工作人群输出多，但知识体系相对稳定、输入弱AI 只是效率工具，重构压力较低

第一阶段不覆盖所有学科，优先选择 AI 使用高频、研究过程有数字化痕迹、知识会反复复用的方向：机器学习、计算生物、数据科学、计算材料等计算密集型科研。这些方向同时具备高代码、高实验密度、高失败成本的特征——也正是科研知识结构（来源、版本、边界、过期）从"负担"变成"信任"的地方。

图 5 · 用户分层　研究生处在输入与输出同时旺盛的阶段，双向链接需求密度最高。

5.2 三层商业对象与定价

商业对象分为三类，职能各不相同：个人 / 开源负责引流和沉淀用户（不是主要收入来源）；课题组（PI）是核心付费群体；学校 / 科研院所做规模化与统一治理。商业模式采用开源 + 付费软件并行：开源降低信任成本、把用户带进真实工作流，付费版是本地运行的织忆软件。

版本价格方向（占位，最终待定）核心价值 / 职能
开源核心免费基础导入、轻量审核、基础复习，接入个人 Agent——引流与沉淀用户
个人版¥29–59 / 月可视化知识管理、复习内化、规则导出；低价订阅，主要服务转化而非主收入
课题组版（核心付费）¥8,000–30,000 / 年 / 组团队传承 + 协同：组内知识共享、经验传承、新人快速上手、减少重复实验开销；面向 PI 的主收入来源
学校 / 科研院所版定制报价私有化部署、权限治理、跨课题组连接与长期传承，规模化采购

这里需要先说清楚节奏：织忆先把核心闭环跑通在个人侧，把个人体验做扎实；知识共享、组内协同这些课题组能力紧随其后，是第一版对外产品的重要组成（只是不在最早跑通的核心闭环里）。它们既很自然能做，价值又很大：当每个学生的能力都被放大、整个课题组再共享这套被放大的能力时，PI 拿到的是团队整体能力的提升。所以在我们的规划里，课题组相关能力被放在很靠前的位置（增长路径见 5.3，能力规划见第六部分）。下面先解释，为什么付费的重心会落在课题组而不是个人。

为什么课题组（PI）是核心付费群体 个人订阅单价低、天花板有限，所以个人侧以开源引流为主、不指望它赚钱。真正的付费力在课题组：PI 的核心诉求是团队的传承与协同，而这恰恰是织忆能直接提供、PI 也能亲眼看见且归因得到的离散收益——新人几天内就能调用组里已沉淀的判断与踩坑、组员之间不再重复同一个实验、组内方法论不随人员流动而流失。比起笼统的"产出变好"（很难说清是不是织忆的功劳），这些可感知、可归因的收益才是 PI 愿意付费的真正理由。全球课题组普遍有充足经费，只要这些收益成立就愿意买单，而学生本身购买力有限。对 PI 的话术是"学生训练 + 项目记忆 + 组内传承"。
图 6 · 商业化框架　个人 / 开源 → 课题组（核心付费）→ 学校 / 科研院所三类对象，分别承担引流沉淀、主力付费与规模化。

5.3 增长路径与飞轮

增长不靠泛流量，而靠使用后产生的知识资产。最早一批用户来自创始人直访和科研社群，重点找已经高频使用 ChatGPT、Cursor、Codex（及本地 Agent）的研究生。增长飞轮是：

开源引流带来真实使用 → 真实协作产生知识资产 → 知识越准，Agent 协作越好、学生科研产出越好 → 组内共享让传承与协同的价值显现 → PI 看到效果、课题组付费 → 进一步带来学校与科研院所采购。

两个机制支撑从个人到课题组的扩散：

  • 导出即分发：用户导出的 AGENTS.md、组会材料和知识包带有织忆生成标记，在课题组仓库与文档里自然形成曝光。
  • 组内共享（刚需功能，规则约束）：课题组内部的知识共享是真实刚需。学生按规则把可共享的部分一键分享给同门，其余知识不公开，对方打开即完成结构化导入。共享在组内自然发生，也让"哪些人正在同一个组聚集"浮现出来，成为课题组版最早的转化线索。

飞轮真正的启动门槛是组内密度——同一课题组要有足够多成员同时在用，PI 才看得到协同与传承价值。因此早期获客优先按组渗透（在一个组里多拉几个人，靠组内一键导入自然带动更多人）；这一条本身也是下面"获客与运营"里要验证的重点。

5.4 竞争对比与差异化

综合对比应围绕"谁管理什么对象"来做。现有产品几乎都是单向连接，各有结构性盲区：

类型管理对象人是否变强Agent 是否变准两端是否同源
知识卡片工具人的学习卡片是否否

"同源"指人端理解与 Agent 端调用共享同一条经过审核的知识。织忆和它们站在不同的层：它管理科研知识如何从协作中产生、被审核、被人内化、被 Agent 使用、再被持续修正。

为什么巨头不做这件事

对"平台为什么不做"，有两个结构性原因：

原因解释
主战场不在这里，机会成本太高巨头的资源和注意力都压在通用模型能力、通用 Agent、企业市场这些更大的战场上贴身竞争。科研知识协同是离主战场很远的垂直层，即使看得见价值，优先级也排不上，做得了但轮不到做。
中立性带来的利益冲突科研知识的价值在于能跨平台流动到用户正在用的任意 Agent（ChatGPT、Cursor、Codex…）；但平台的利益是把用户和知识锁在自己生态里。让 OpenAI 去做一个"帮你把知识带到 Claude / Cursor 也一样好用"的中立层，本身就和它的根本利益相悖。

我们的应对是把平台当执行层来拥抱，不和平台抢通用层，做跨平台的科研知识控制层。导出物只是某个时点的快照；知识的版本、冲突识别和持续修正仍然发生在织忆内，因此开放导出与长期留存并不矛盾。需要强调的是，巨头"不做"更多出于定位与利益，它给我们的只是一个时间窗口；真正的壁垒要靠在这个窗口期里积累（见 5.5）。

5.5 护城河

必须诚实：这件事最大的特点是创新性强、目前没人做过，所以现阶段最现实的护城河是先发占位——趁巨头"不愿做"的时间窗口，率先把"人—Agent 双向科研知识层"跑通、占住市场空间，并从第一天起积累只有真实科研决策乘以时间才能换来的校准数据。先发本身不够硬。真正越积越深、抄不走的长期壁垒来自三个方向（均属未来规划、不在当前 MVP，落地内容与节奏见 6.3），下表只论证为什么抄不走：

方向为什么抄不走
① 输入端精细化调优它靠"按学科的专家定制 + 审核复利"两层积累，是真实科研决策乘以时间换来的资产，且只长在用户本地闭环里——单把数据导出也搬不走。越用越准 → 越离不开，时间越久差距越大，后来者无从从头追赶。
② 输出端交互多样化把复盘嵌进通勤、散步等场景，沉淀的是长期使用黏性与切换成本——本身不直接构成壁垒，但持续抬高用户离开的代价。
③ 基于 MCP 的定制化输出面向不同学科与科研场景的定制化输出，其质量依赖①积累的校准资产，因此不是单点功能能照搬：别人即便复制交互形态，也复制不了背后越积越准的抽取。

三方向的落地节奏与依赖见 6.3。此外，本地优先、可导出可删除、默认不上传训练的隐私边界，是科研未发表场景下通用平台难以复制的信任壁垒，构成上述方向的底座。需要特别澄清：上述审核复利只在本机或用户授权的课题组范围内沉淀，绝不把用户数据回收用于训练我们的抽取或其他模型。系统变好的方式是在每台机器、每个小组内积累校准复利。

06 未来规划

当前 MVP 只做一件事：把中间的核心闭环跑通，先证明"被保存的知识能真实改善未来 Agent 的工作结果"。真正构筑护城河的能力（输入精细化调优、交互多样化、MCP 定制化输出）属于此后的未来规划。

6.1 产品路线图

产品按三条优先级与三个构建切片推进，每片产出可运行、可测试的软件：

切片内容

对应的能力优先级为：第一优先级（首页、抓取控制台、待审、知识库、复盘中心、Agent 记忆注入）→ 第二优先级（知识图谱、设置）→ 第三优先级（掌握进度深化、语音复盘）。

关键衡量指标聚焦于"保存的知识有没有在未来工作中产生真实回报"，而非每天打开率：连续 14 天处理率、候选完成率、保存知识 7 天内复用率、删除率（衡量抽取质量）、空日接受度。任何一条长期不成立，特别是第一条，应停止或转向更轻量的形态。

获客与运营（尚待验证）

宣传与运营目前只有方向、还没有验证：可能的渠道包括科研社群、导师与同门口碑、开源项目曝光。计划先小范围投放与访谈，实测哪条渠道获客成本最低、转化最好、以及如何在单个课题组内做到多人采用（组内密度），再据此调整，而不是一上来就铺开。这部分作为待验证项持续滚动修正。

6.3 能力扩展方向

课题组共享与协同是商业上的主方向，紧随核心闭环、是第一版对外产品的重要组成；输入精细化、输出交互、MCP 定制化三条则构成长期护城河（5.5 已论证为什么抄不走）。下面给出各自的落地内容与节奏：

方向落地内容依赖 / 节奏
课题组共享与协同（商业化主方向）把个人沉淀的知识按规则在组内共享、让新人快速继承、减少重复实验；向上扩展到学校 / 科研院所的治理与私有化部署。这是面向 PI 付费的核心价值（对应 5.2 / 5.3）。紧随核心闭环，是第一版对外产品的重要组成；依赖个人侧体验已扎实、组内达到一定使用密度。
① 输入端精细化调优邀请各学科科研人员参与输入设计，研究学科知识能否细分为若干类别；通过分类与提示词调优，让 AI 对不同学科的抓取与理解更准。在此之上叠加审核复利：审核环节产生的拒绝、修正、漏提 / 错提反馈，作为校准样本在本机或用户授权的课题组内回流到抓取与判类，让引擎越用越贴合这个人、这个组（此回流只在用户本地或其授权的组内，不上传、不用于训练我们的模型）。MVP 之后启动；依赖一定量真实审核数据与各学科种子用户，可在切片三之后逐学科滚动推进。
② 输出端交互多样化在文字问答之外提供语音问答等更自然的交互，让复盘可以在通勤、散步、睡前等低视觉负担场景轻量完成。对应第三优先级（语音复盘）；依赖复盘中心已稳定。
③ 基于 MCP 的定制化输出作为完整框架的一部分，用 MCP 实现超越简单记忆的定制化知识输出（综述、调研报告、知识包、研究计划、跨领域分析等）；语音教学也在此阶段。这一需求在用户访谈中被反复提及。依赖①的校准资产成熟；置于双端交付（切片二）之后。

其余配套方向按需推进：知识类型化与分级、卡片→Memory 转换层、浏览器插件取数以覆盖更多来源。

如果我们做成，AI-native 研究者将不再需要在聊天记录、笔记和规则文件里反复拼接自己的研究知识——
而是把科研协作中生长出的概念、方法论、经验与判断，沉淀成一套人和 Agent 都能持续使用的知识资产。
